## Decision

The independent screen found **no external evidence proving >30 wall Hz actions plus three distinct fresh 960×600 camera frames under an active Quest XR session**. It also found no credible reason to abandon the current stock renderer first. The strongest near-term composition remains CPU PhysX for this small robot count, one shared Kit/XR scene, explicitly retained dataset products, bounded-lag native producer capture, and stock H.264 or GPU encode. CPU versus GPU physics must remain a measured selection, not a universal claim.

The fastest credible route from the parent-reported measurements is CPU PhysX + Minimal rendering + IK + native compressed capture. Parent reported 52.39 Hz in the XR experience with CloudXR enabled but `xr_status.enabled=false` and no Quest. This is a promising **no-client screen**, not a Quest result. Parent also reported GPU PhysX 39.31 Hz with Minimal, CPU PhysX 73.72 Hz without IK, and CPU RealTimePathTracing + IK 37.68 Hz. These numbers were supplied by the parent, not independently recomputed here; exact artifacts must accompany them. Retaining every real fresh camera generation and allowing a measured small lag is more promising than forcing a zero-delay renderer fence on each action.

The strongest genuinely missed reusable component is installed **`isaacsim.streaming.rtsp.RTSPStreamWriter` 0.1.5**. It owns existing-product attachment, raw CUDA/native H.264 routing, server lifecycle and optional encoded SEI. It is worth screening before a new CUDA/Vulkan exporter or media framework. Its metadata and failure handling do **not** meet dataset admission requirements by themselves.

## Important corrections and counterevidence

### Current Isaac Lab keeps external cameras in XR by default

The February 2026 Quest thread reports camera removal and synchronous read stalls. That advice is version-specific: installed Lab 17.0.2 `scripts/tools/record_demos.py:127,148–152,367–372` enables external cameras by default and calls `remove_camera_configs` only when `--disable_external_cameras` is supplied. `teleop_se3_agent.py` likewise has a conditional call. The installed helper `isaaclab_teleop/xr_cfg.py:112–148` still says extra cameras cause performance issues and strips CameraCfg plus policy observation terms, but existence of this helper does not establish its execution.

Therefore a screenshot or smooth XR session from a generic upstream teleop example must be checked for camera-retention flags and actual products. Conversely the exact pin already supports retaining cameras without a private patch. Our project entrypoint should retain its own shared lifecycle/label semantics. [Primary Quest discussion](https://forums.developer.nvidia.com/t/how-to-get-camera-input-when-vr-is-running/358922).

### Minimal mode integers contradict within the installed SDK

Installed `omni.rtx.settings.core-0.7.1+00c488ae/.../minimal_widgets.py:19–22` and Lab `isaac_rtx_renderer.py:67–84` agree on `0=No Rendering`, `1=Constant Diffuse`, `2=Texture Diffuse`, `3=Diffuse/Glossy/Emission`. Installed `SimulationApp` docstring at line 164 and the official September 18 Isaac Sim docs instead say `0=RT2 reference`, `1=Diffuse/Glossy/Emission`, `2=Textured Diffuse`, `3=Constant Diffuse`, `4=No Rendering`. `simulation_app.py:644` writes the supplied number unchanged.

Mode 2 agrees across both sets. Modes 0/1/3/4 need numeric readback **and actual pixels**, not inference from documentation or a Lab alias. Lab's `simple_shading_full_mdl` resolves to integer 3 and writes a **global** `/rtx/minimal/mode` during product creation (`isaac_rtx_renderer.py:345–347,440–451`). Different camera aliases are not proof of independent per-product quality settings; last creation may affect the common renderer and XR eyes. No supported independent quality-mode boundary for eyes versus dataset products was established by this audit.

RTX Minimal omits indirect light transport and supports only the first distant light and hard shadows. Its strongest numbers therefore need an explicit fidelity witness. Global disabling of rendering, black RGB, reduced image dimensions, interpolation/DLSS frame generation or dropping camera generations cannot meet the requested target. [Official rendering modes](https://docs.isaacsim.omniverse.nvidia.com/latest/reference_material/rendering_modes.html).

### A seemingly excellent public tiled-camera result is not fresh-frame throughput

Pinned `jspaulding-nv/isaac-sim-tests@de297c2d19b9f3b31299b65073f115e4e4ae9973` publishes Isaac 6.0.1/Kit 110.1.2 tests on PRO 5000 and PRO 6000 Blackwell. Full Streaming reported 600/600 buffers for 16 cameras at 320×240; standalone reported no RGB. That is 1.229 Mpx total versus our 1.728 Mpx, without our robot scene, active Quest, action recording or 960×600 per camera. It is a useful **headless-versus-experience lifecycle warning**, not an applicable performance benchmark.

Raw retained results have observed durations 19.896891078 s (PRO 5000) and 71.79100765 s (PRO 6000): arithmetic ratios are 30.155 and 8.358 delivered-buffer calls/s. They are unlike hosts and broad duration fields; they do not rank GPUs. More critically, `tests/visible_tiled_camera_replay.py:244–282` increments its delivery counter whenever `get_data` is non-None, then copies `.numpy()` into a CPU UI provider. It does not compare renderer frame IDs or camera-specific generation clocks. A moving marker plus browser video proves some motion, not 600 unique renders. T5 reports 60/60 complete output in Full Streaming while standalone misses 4–5/60; surface choice affects completeness too. [Pinned test source](https://github.com/jspaulding-nv/isaac-sim-tests/blob/de297c2d19b9f3b31299b65073f115e4e4ae9973/tests/visible_tiled_camera_replay.py), [result](https://github.com/jspaulding-nv/isaac-sim-tests/blob/de297c2d19b9f3b31299b65073f115e4e4ae9973/results/t4-tiled-camera-replay.json).

### Headless does not universally remove rendering cost or hazards

Isaac 6.0 issue #701 reports a headless surfaceless viewport path stalling around ten seconds per frame. This is a reporter's failure, not a reproduced 6.1 defect. Together with the public Full Streaming split, it argues for examining the actual owned products and presenting lifecycle rather than assuming `--no-window` is faster. Disable or remove only an unneeded owned viewport/product; do not disable all Hydra textures or enumerate/delete XR products to make a camera benchmark pass. Existing project camera suspension is scoped to dataset products and is useful for state-only recording, but cannot satisfy live RGB recording. [Issue #701](https://github.com/isaac-sim/IsaacSim/issues/701), [NVIDIA product control guidance](https://forums.developer.nvidia.com/t/disable-camera-rendering/249768).

## Native streaming route: precise supported boundary and remaining gaps

Installed `isaacsim.streaming.rtsp/impl/rtsp_writer.py`:

* `__init__`: `encoding='raw'` requests `LdrColor(device='cuda',do_array_copy=False)`; H.264 requests `init_params={'compression':'h264'}` plus `IsaacReadSimulationTime(resetOnStop=True)`.
* `write`: handles one LdrColor product, increments `_frame_num` before pushing. Three cameras need three writer instances, each attached to its existing product; do not create duplicate products merely to stream.
* `_push_frame`: gets Warp pointer, uses packed four-byte pitch, calls native `stream_video_cuda_buffer`. This reuses upstream GPU routing; no guessed pointer from RpResource or Python-object address.
* `_push_encoded_frame`: copies compressed bytes, skips empty arrays, builds SEI and calls `stream_video_pre_encoded_with_metadata`. SEI contains `publish_sim_time_ns`, derived wall-anchor timestamp and callback frame number.
* `_stream_failed` suppresses further attempts until detach. Native stream-call return value is not inspected. Empty packets still consume a callback frame number. Those are important loss/accounting boundaries.
* detach stops server and resets failure/numbering. This is a preview/streaming lifecycle, not a complete durable multi-camera/action commit protocol.

The SEI simulation-time annotator is **not independently established as the capture state**. A queued renderer can supply older optical content while a separate timestamp is current; bounded lag requires resolving source generation rather than relabeling. Raw mode has no SEI; timestamps synthesized by adding sim time to a first wall anchor are not measured acquisition latency. Use completion-generation metadata and a moving optical phase witness across all cameras, camera mounts and reset boundaries. Retain encoded packets before transport if durable recording is required, or prove receiver packet/decode completeness. RTSP transport adds buffering and loss modes; no reason to route through a network protocol solely for recording if the existing native writer already owns encoded bytes. [Isaac 6.1 RTSP owner](https://docs.isaacsim.omniverse.nvidia.com/6.1.0/digital_twin/rtsp_camera_streaming.html).

## Stereolabs: real new upstream optimizations, with limitations

Pinned `stereolabs/zed-isaac-sim@0164268ca123fa4549fc9d2062c1fd55cf7996dc` is extension 5.2.1 for Kit 110.1.2, not our declared Kit 110.3. Its 5.2.0 changelog says default stream cadence changed 60→30 and cameras now render at target FPS using Isaac 6 multi-tick scheduling. A default 30 Hz sensor cannot establish **strictly greater than 30**; set and read back a suitable target. Tick rate is simulation-time scheduling, not guaranteed wall throughput.

`OgnZEDSimCameraNode.cpp` has a real GPU-input path: slots use CUDA allocation, producer does device-to-device copy rather than PCIe readback, then a consumer thread encodes/sends. It still calls `cudaStreamSynchronize` in the producer at line 875. This is upstream async encode, not completely asynchronous extraction and not literal zero-copy. Free slot acquisition can decline frames; loss must be accounted for. Optional Sim2Real adds GPU work and may fall back to host processing; do not compare enabled and disabled quality as identical routes.

5.2.1 explicitly fixes IPC/BOTH crashes a few seconds into Linux stereo streaming and failure recovery. A short successful IPC smoke on 5.2.0 is consequently weak. A version label is not ABI compatibility with our pinned Kit. The tensor helper remains native IsaacLab Camera rather than an alternative renderer; `make_stereo_camera_cfgs` even warns that `spawn=None` cameras inside a referenced robot USD may remain at authored pose, so correct robot-attached motion must be witnessed. Three mono policy cameras should not acquire six stereo views just to reuse a ZED SDK recording route. [Pinned changelog](https://github.com/stereolabs/zed-isaac-sim/blob/0164268ca123fa4549fc9d2062c1fd55cf7996dc/exts/sl.sensor.camera/docs/CHANGELOG.md), [pinned C++ source](https://github.com/stereolabs/zed-isaac-sim/blob/0164268ca123fa4549fc9d2062c1fd55cf7996dc/exts/sl.sensor.camera/plugins/nodes/OgnZEDSimCameraNode.cpp).

## Minimum discriminating experiment

1. Keep the same exact scene, two articulations, collision/controller settings, camera mounts/intrinsics, IK path, output quality and source action processors. Compare CPU/GPU physics without changing label/native mapping or substep meaning.
2. Start with retained dataset products plus no Quest, then active Quest connected, moving HMD/controllers and eyes actually rendered/encoded. Read active XR state and product list in the run manifest. The parent’s no-client 52.39 Hz establishes no eye/input workload.
3. Compare native compressed producer, raw CUDA upstream writer and existing source-aligned writer. Add one tiled product only as a separate controlled variant. Do not add stock CameraSensor on top of existing camera owners just to gain a get_data API.
4. Count accepted action labels and **fresh real render completions** independently for all three roles over long intervals. Record source generation, optical phase and latency distribution; detect repeats/missing packets, first/last frames and reset mixing. Decode all retained encoded frames once, outside the measured producer.
5. Permit an explicit finite lag/queue. A worker that falls behind indefinitely cannot satisfy sustained >30 wall Hz; include drain time and queue high-water mark. Dropping the oldest snapshot is not an implicit permitted replacement for the requested fresh dataset cadence.
6. If a native same-process path cannot sustain the Quest target, test immutable snapshot OVRTX first. Only then consider a second GPU or different renderer/fidelity, with explicit tested scope and environmental declaration.
