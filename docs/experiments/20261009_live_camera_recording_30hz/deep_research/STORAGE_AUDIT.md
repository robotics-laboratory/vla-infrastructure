## Decision

**Prioritize the stock three-camera compressed producer plus a bounded owned-packet writer. Preserve existing snapshot/HDF5 V2 state recording.** A single HDF owner can remove periodic write stalls if profiling warrants it; CUDA IPC and GPUDirect Storage are later alternatives, not prerequisites for >30 wall Hz with Quest. None of these transports solves renderer source-phase ambiguity. Small delivery lag must retain source identity, with explicit missing/rejected joins rather than pairing delayed pixels to latest action.

The useful distinction is where the remaining serialization happens: (1) simulator/Fabric observation read and freeze; (2) causal validation/transition construction; (3) renderer completion/readback/encoder; (4) storage. A writer thread can overlap (4). An owned GPU ring can overlap consumer operations after (3) has published a ready, immutable image. Neither makes the main-thread simulator read asynchronous.

## One owner for HDF, threads before process transport

Use existing upstream `SessionStorage` in a single worker, initialized/opened/ended/closed by that same owner. Main-thread capture and causal admission remain authoritative. After causal commit, transfer a complete immutable9group bundle; worker appends allgroups, advances frame once, and flushes. At seal send an ordered barrier, await queue drain and last persisted sequence, then upstream end/close, terminal-successor output and existing post-close verification/hash/finalization. Retain session-owned Recordable handles on simulation thread. Make enqueue accepted count distinct from persisted count; no success result until equality and verification.

h5py’s global `phil` lock serializes h5py API calls even across different datasets/files, but its docs support pipelining h5py work with nonh5py work in other threads. Therefore use one writer, not97parallel channel writers. The Python append/validation loop still competes for GIL; C HDF IO may overlap. Any full causality check moved offthread changes the rejection/feedback boundary and needs explicit design; only completed admitted bundles should cross initially. [h5py threading](https://docs.h5py.org/en/stable/threads.html).

Suggested initial bounds are experiment choices, not qualification limits: state queue128rows(~1.032MB schema bytes) and128-row stockbuffers(~1.032MB), plus object overhead; 50Hz queue age ceiling100ms should fail long before all128rows accumulate. Emit queue depth/oldest age/enqueue_us/write_ack_us/flush_ms/persisted-source watermark. Capacity bounds memory; age bounds lag. A consumer with sustainable rate≤producer eventually fills every finite queue; buffering cannot fix this. If failed, reject admission of next transaction before physical actuation where possible, request existing recording abort and retain partial result/failure; do not deadlock XR app thread with unbounded `queue.put()`/join. Test slowdisk, injected exception midgroup, worker death, seal while full, reject, reset, episode rotation.

A dedicated `spawn`/exec writer process removes writer Python GIL competition and isolates encoder/storage crash, but requires serializable schemas/arrays and explicit ownership of file. Never fork a live CUDA/Kit/HDF process and inherit its file/context. State8063bytes/row is small enough that conventional CPU IPC may be sufficient; use measured pickle/queue costs before sharedmemory. SharedCPU image ring is for rawpixels: slots never reused before consumer ACK. Do not require a new service/container/environment or RPC merely because a process is useful. A storage adapter is a bounded composition around upstream, not a replacement format/recorder.

## Owned CPU and CUDA image rings

Native compressed packets are already CPU byte payloads. Freeze those bytes with provenance in the producer callback, then transfer them to a bounded append worker. This avoids raw RGBA readback and a second GPU upload. Preserve the current state HDF plus compatible media streams and their source mapping; do not add large image HDF tracks solely to make one file.

For raw CPU images, copy into preallocated owned slots before queueing. If the CPU source API already did synchronous D2H, the writer thread cannot hide that earlier readback. Overlapping D2H itself needs a ready owned GPU source, preallocated pinned CPU destination, a copy stream, cudaMemcpyAsync and a completion event. The CPU cannot read before completion; neither producer nor consumer may overwrite/free before the final ACK. Async D2H to pageable memory can synchronize, so the Async suffix alone is insufficient. [CUDA 12.8 sync behavior](https://docs.nvidia.com/cuda/archive/12.8.1/cuda-runtime-api/api-sync-behavior.html).

Installed Replicator 1.13.36 `annotators.py:1863` documents `get_data(..., do_array_copy=False)` and says a copy is necessary when data must persist for an asynchronous backend. Constructor default copy=True differs from explicit get_data default=False. Submitting a borrowed CPU view to a worker is unsafe; use do_array_copy=True or complete the owned copy before producer reuse. A numerical Warp GPU pointer does not establish readiness or lifetime.

Parent-isolated OVRTX 0.5.1 `types.py:325` provides a stronger contract: GPU map may return before producer completion. map(sync_stream=S) or wait_on(S) inserts the producer event wait, then consumption must use S. CPU map is ready on return. unmap(stream=S), or an explicit completion event, retains interest until the downstream work can finish safely. Existing views remain alive while referenced; renderer destruction force-unmaps outstanding mappings. A small adapter can map each of three views on a copy stream, queue D2D into owned slots, unmap with that stream and record slot readiness. Keep renderer and source owners alive until copying completes. Use stream-specific ordering rather than global cudaDeviceSynchronize; do not reset/destroy while exports remain active. This is installed source inspection, not GPU runtime verification.

An initial raw ring trial can use four three-camera bundles: 4×3×960×600×4=27.648 MB unpadded GPU or CPU storage. GPU plus pinned CPU tiers total 55.296 MB, excluding encoder surfaces and allocation alignment. Four slots represent about 80 ms of arrivals at 50 Hz, but occupancy includes production and consumption. A 60 ms age limit is an initial experiment choice; the final limit must meet the user's small-lag requirement. Source history must cover the bound plus reset fencing. Do not implement a hardcoded frame-minus-two join.

## CUDA IPC: useful after ownership, not an assumed export of a borrowed Kit pointer

Legacy IPC exports cudaMalloc memory through cudaIpcMemHandle_t, rather than sending a process-local pointer. The importer opens once and receives its own pointer. Share ready/done events created with Interprocess|DisableTiming. Retain the allocation until importer close and all queued consumption complete. Python references do not protect native allocation lifetime; exporter death invalidates mappings. Managed memory is unsupported by legacy IPC. CUDA 12.8 documents Windows with caveats while the latest guide restricts legacy IPC to Linux; the target is Linux. Use compatible drivers/runtimes and retain GPU UUIDs rather than assume equal ordinals. [IPC guide](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/inter-process-communication.html), [CUDA 12.8 API](https://docs.nvidia.com/cuda/archive/12.8.1/cuda-runtime-api/group__CUDART__DEVICE.html), [NVIDIA lifetime forum](https://forums.developer.nvidia.com/t/what-will-happen-if-i-create-interprocess-memory-by-cudaipcgetmemhandle-while-no-other-program-process-it/302442).

Reuse [simpleIPC](https://raw.githubusercontent.com/NVIDIA/cuda-samples/master/cpp/0_Introduction/simpleIPC/simpleIPC.cu): cudaMalloc/export/import, stream wait/event record, consumer close, owner wait/free. The sample prevents advancing ahead and clobbering an event generation. A ring needs slot_id and monotonic generation; publish its CPU descriptor after recording readiness. Do not record ready(n+1) while a consumer still depends on n. The ready fence orders pixel access; CPU ACK without GPU completion does not permit slot reuse. A useful lifecycle is FREE → PRODUCING → READY → CONSUMING → FREE, with generation checks both ways. Detect worker death and fail the recording. Startup must handshake GPU UUID, size, format, stride and consumer readiness.

The VMM alternative [memMapIPCDrv](https://raw.githubusercontent.com/NVIDIA/cuda-samples/master/cpp/3_CUDA_Features/memMapIPCDrv/memMapIpc.cpp) uses cuMemCreate, requested exportable FD handles, allocation granularity, import/map/set-access and unmap ownership. Linux FDs must be transferred with SCM_RIGHTS or equivalent, not copied as an integer to another process. The reference uses exec-spawn. These current sources live under cpp/; old Samples/ URLs returned 404. Remote commit identity is not pinned and performance was not measured.

The useful candidate is a bounded ring of dedicated owned cudaMalloc or VMM allocations. Copy renderer output D2D once, then let the encoder worker import those slots. A borrowed Warp/Kit suballocation may not be exportable, and imported Vulkan memory is not a guaranteed cudaMalloc IPC allocation. The legacy guide recommends allocation sizes aligned to 2 MiB to avoid sharing unrelated allocator suballocations. Applying that policy rounds a 2.304 MB camera view to 4 MiB; it is not a renderer pitch requirement.

## Vulkan external memory is a separate capability boundary

[CUDA graphics interop](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/graphics-interop.html) and [vulkanImageCUDA](https://raw.githubusercontent.com/NVIDIA/cuda-samples/master/cpp/5_Domain_Specific/vulkanImageCUDA/vulkanImageCUDA.cu) use exportable VkDeviceMemory, allocation-size-compatible CUDA import, matched format/layout, external Vulkan semaphores, CUDA wait/signal and Vulkan barriers. CUDA and Vulkan must identify the same physical GPU. A successful Linux opaque-FD CUDA import consumes that FD. A tiled VkImage cannot be treated as an arbitrary linear RGBA pointer. The dedicated-allocation flag must match actual Vulkan allocation; [this NVIDIA forum case](https://forums.developer.nvidia.com/t/cuda-vulkan-vkimage-interop/278691) illustrates the failure.

The samples create exportable resources at allocation time. They do not give Kit Hydra RpResource a public export method. The media audit found no such method in installed Python APIs; this task found no additional supported export boundary. A Vulkan FD/semaphore path therefore needs an upstream export API or supported plugin before a thin adapter is justified. That is larger integration work than existing Replicator CUDA output or stock compressed payloads. CUDA IPC does not automatically export arbitrary Vulkan textures.

## GStreamer: upstream ring ownership exists, installed ABI still decisive

[GstCudaMemory](https://gstreamer.freedesktop.org/documentation/cuda/gstcudamemory.html) offers `gst_cuda_allocator_alloc_wrapped(context, stream, info, dev_ptr, user_data, notify)` since 1.24. It wraps CUDA memory with explicit stride, offset and size. Supply a release callback to return the owned ring slot; without `notify`, the allocator frees the pointer by default. VMM allocation/export also exists. These APIs can support a compatible modern nvcodec consumer. They do not prove that Kit’s adapted encoder plugin, based on approximately 1.20 sources, exposes or accepts that memory type. Keep the media audit’s distinction between system GStreamer 1.20.3 and Kit’s bundled 1.24.12 runtime.

[appsrc](https://gstreamer.freedesktop.org/documentation/app/appsrc.html) references the buffer and queues it. Configure explicit caps, time format and source PTS, and respect enough-data/need-data. A successful push is not completion: the slot can return only after the final GstMemory reference is released. [queue](https://gstreamer.freedesktop.org/documentation/coreelements/queue.html) creates a worker thread, but its byte/time bounds can fill before its buffer bound. An explicit four-buffer trial uses `max-size-buffers=4 max-size-bytes=0 max-size-time=0 leaky=no flush-on-eos=false`. Choose deliberately whether that is per camera or for a three-view bundle. The default 10 MiB byte limit cannot hold four three-view RGBA bundles. Lossy preview can use a leaky queue; dataset camera drops must invalidate the corresponding joins explicitly. Calling blocking appsrc push on the Kit thread risks XR stalls. A bounded feeder worker must propagate bus errors, EOS and drain timeout. Queues do not supply renderer fences or source alignment.

## GPUDirect Storage: genuine API, wrong first target here

[GDS overview](https://docs.nvidia.com/gpudirect-storage/overview-guide/) targets GPU-to-storage DMA, particularly GPU-resident streaming data. Current state snapshots, validation and hashing use CPU arrays. Uploading a 952-byte observation to make GDS applicable adds another transfer. Stock encoder packets are CPU bytes; moving those to the GPU for disk transfer would also add H2D. Raw-image GDS is plausible only if raw persistence is required and measured storage/D2H dominates. This is an inference from the current path, not a GDS benchmark.

[cuFileWriteAsync](https://docs.nvidia.com/gpudirect-storage/api-reference-guide/index.html) is a real stream-ordered API with nonblocking CPU submission. The actual completed byte count must be checked and the GPU buffer retained until completion. Filesystem, storage topology, registration, memory/alignment and compatibility fallback matter. `libcufile` presence alone would not prove a direct DMA path. No GDS support probe ran here.

[hpc-io/vfd-gds](https://github.com/hpc-io/vfd-gds) is an actual HDF5 VFD plugin. Its README states that an unmodified CPU HDF application behaves like sec2 POSIX IO; GDS requires a device-allocated buffer passed to H5Dwrite/read. Chunk caching, filters and fill paths may introduce GPU/CPU copies. It requires a native build and HDF5 >=1.14. This does not accelerate SessionStorage’s NumPy chunks through configuration alone. Preserve the existing HDF V2 format rather than create a new GPU format for this workload.

## Async HDF VOL: real upstream, not a free h5py switch

[Async VOL](https://hdf5-vol-async.readthedocs.io/en/latest/) schedules a dependency graph in a background worker. [Setup](https://hdf5-vol-async.readthedocs.io/en/latest/gettingstarted.html) requires a thread-safe HDF build and Argobots. Implicit mode is recommended only for testing and keeps dataset operations synchronous by default. Explicit mode uses H5Dwrite_async/EventSet. Write buffers must stay immutable until H5ESwait, unless built with a memory-copy option that adds CPU copy and memory use. Completion/error handling remains necessary. The current h5py SessionStorage does not call those APIs. [Known issues](https://hdf5-vol-async.readthedocs.io/en/latest/issue.html) include metadata overhead, multifile EventSet issues and a synchronous get-space workaround. This is a larger environment/API change than one owner thread around the existing writer. Do not enable HDF5_VOL_CONNECTOR or LD_PRELOAD in production as a benchmark shortcut.

## Failing bounds, acceptance and rollback

Every queued variant needs all three views for every accepted source, decoded counts, unique sequences, explicit source-bound pose/intrinsics/episode/reset/generation, capture-to-delivery/persistence age histograms, bounded depth and oldest age after warmup, and final drain included in the result. Reject and terminal-successor behavior must remain exact. Failure cannot silently continue writing. Producer and consumer must both sustain the approximately 50 wall Hz screening workload using the selected quality and active XR rig without Quest, then strictly >30 wall Hz in an authorized Quest 3 test. Mean alone does not establish bounded lag; queue growth, tails and each camera’s age matter. This memo does not qualify that target.

Recommended order:

1. Profile hdf_append and hdf_flush separately in the current full recording.
2. Add native packet ownership and a bounded file writer; prove source phase and decoded counts.
3. Introduce one HDF owner only if periodic flush stalls materially affect the target.
4. Consider a pinned raw-image ring if stock compression cannot meet requirements.
5. Use CUDA IPC only if process isolation or removal of GIL contention has a measured benefit.
6. Consider Vulkan export, GDS or Async VOL only after identifying a supported public boundary and a specific bottleneck.

Rollback selects the known synchronous state writer/media path through an experiment flag. Drain or abort workers before closing native owners. Remove process-specific environment overrides and experiment imports; do not edit SDKs, drivers or global settings. Preserve failed artifacts and the last persisted source watermark. Source/config hashes, experiment registration and exact pins remain the root agent’s responsibility. This agent changed no project runtime code; all outputs are under `/tmp`.
